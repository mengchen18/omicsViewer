## 2. Confirmed findings (each is a fix-plan candidate)

**F1 — The unaddressable 122.** Every user-facing widget that is not a
store binding is beyond the LLM's reach, with per-widget rejection
receipts recorded. Breakdown (examples in `results/*dom*`):
- 10 module action buttons (`geneshot submit`, `string run`, table
  `clear` ×3, heatmap clear, …) — the store has no event/action kind.
- 8 download controls (xlsx export, per-table csv).
- 7 quick-view badge buttons (semantic alternative exists:
  `set_scatter_view(quick_view_id)`, recorded per badge).
- 5 AI-assistant own controls (intentionally out of scope, recorded).
- 4 snapshot-modal controls; 1 dataset selector (`app-selectFile`).
- 4 `searchon` gene-highlight pickers (the gap demonstrated earlier in
  `verify_search_highlight.mjs`; one per scatter space).
- 79 attr4/triselector component inputs + misc (content of these is
  covered semantically by their parent cascade bindings; the individual
  selectize inputs themselves have no addressable binding — noted per
  case).
- 4 plain buttons (Shortcut/Custom mode-label buttons, plot-type tabs).

**F2 — Categorical-axis freeze (>30 s, real).** Writing a categorical
annotation (2 702 unique values) onto a scatter axis via
`set_widgets` blocks the browser main thread for ~200 s (plotly layout
of 2 702 categories, software rendering). Both `x_analysis` and
`x_variable` cases timed out (198 s / 199 s). A model that points an
axis at e.g. `Gene.name` effectively freezes the app for minutes.
Numeric axis switches are fast (<3 s). → `results/028-*, 030-*`.

**F3 — dyn-heatmap discovery + validation hole (real, proven).**
While the Dynamic-heatmap tab is inactive:
- capability records expose **no allowed values** (choices providers are
  tab-state-dependent) → the model cannot discover valid values;
- worse, `set_widgets` then **accepts garbage** (`annot_col:
  ['GARBAGE|X|Y']`, `col_sort_by: 'NOT_A_SORT_MODE'` both applied) because
  the validator treats NULL allowed as "no constraint";
- the garbage persists in the store while the UI shows `[]` — store/UI
  divergence. With the tab active, validation works correctly.
→ `supplementary_dyn_heatmap.json`, `results/*dyn_heatmap*no-probe*`,
`results/*dyn_heatmap*annot_col*`.

**F4 — Table `columns` write anomaly (bug-suspect).** Generic
`set_widgets` on `dataspace.tab_*.columns` reports `applied`, but the
applied value is recorded as a **scalar string** (the sent 1-element
array mangled) and the store read-back immediately after is **NULL**
(store/UI echo race suspected). `page` writes DO reach an initialized
table (live: `start` 0→25) but were no-op probes (page 1 == displayed
page) in the sweep. → `results/079-*, 083-*, 087-*`,
`spotcheck2_results.json`.

**F5 — Conditional/dead-end widgets (real).**
- `resultspace.sample_general.survival_censor`: the censor slider does
  not exist in the DOM until a survival-type variable is selected
  upstream; the store write cannot reach a not-yet-rendered input.
- `resultspace.stringdb.selected_row`, `resultspace.fgsea.selected_row`,
  batch `*_selected_row`: row choices are empty until an upstream Run
  button is pressed — which the agent cannot do (F1). Operability
  dead-end chains: value widget depends on unpressable action.

**F6 — expr-heatmap congestion (suspected artifact, kept for review).**
`row_sort_by`/`annot_row` writes produced no observable input change
within the window; suspected browser congestion from the 2 702×60
re-render. Not re-verified live. → `results/022-*, 026-*`.

**F7 — no-distinct-value cases (benign).** 8 cascade/PTM bindings where
the only allowed value already equals the current one (single-valid
subset under the chosen analysis; PTM's only analysis `SeqLogo`). The
agent CAN address them; the sweep had nothing different to write.

## 3. What works (important for the fix plan)

- 141/170 store bindings: full round-trip `set_widgets` → store → push →
  browser input change, most < 1.5 s.
- All 18 semantic-tool cases succeed, including deliberate error paths
  (bogus pathway id returns a suggestion-bearing rejection).
- Single-key triselector cascade writes DO reach the UI (verified live
  after the sweep windows were starved by F2's congestion:
  `spotcheck2_results.json`) — the earlier `no-ui-effect` batch for
  attr4/xax analysis/subset levels was an instrumentation artifact of
  that congestion, reconciled to success with `verification:
  spotcheck`.

## 4. Method notes (so the log is interpretable)

- The hidden `OMICSVIEWER_TEST_HOOKS` module is the EXACT server pathway
  of the assistant tools (see README table) — every case is a faithful
  LLM tool call.
- 30-s rule: enforced on wall-clock operation→observable-effect
  (`duration_ms`), because `waited_ms` is unreliable when the browser
  main thread blocks mid-poll (F2).
- Status reconciliation: raw sweep observation → noise-filtered
  revalidation (hook-panel inputs excluded) → live spot-checks for the
  suspicious classes; every reclassification is recorded in the result
  file (`_status_before_30s_rule`, `_status_before_revalidation`,
  `verification`, notes).
- Known enumeration caveat: DT per-column filter `<input>`s were not
  captured by the DOM selector (0 found); their capability is covered
  and verified via the `column_filters` binding and
  `set_table_view` cases instead.

## 5. Fix-plan entry points (from the earlier static evaluation + this evidence)

1. Action/event tier in the store + `run_control` tool (F1: 10 action
   buttons, F5 dead-end chains).
2. Bind the four `searchon` pickers (F1; demo in
   `verify_search_highlight.mjs`).
3. Make dyn-heatmap (and any module) choices providers
   activation-independent + reject when allowed is NULL (F3).
4. Guard/guardrail categorical scatter axes (F2): validate axis
   cardinality at write time or fall back to a bounded rendering mode.
5. Investigate the table `columns` scalar-mangle + read-back NULL echo
   race (F4).
6. Render-independent bindings for conditional widgets (survival censor)
   or capability records that state preconditions (F5, F6).
7. Discovery enrichment (labels/help/panel context) — unchanged from the
   static evaluation; the sweep's capability dump
   (`artifacts/capability_registry.json`) is the baseline corpus.
